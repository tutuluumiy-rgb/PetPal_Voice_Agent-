## 1. preRoll 锚点与取值修正（✅ 已实施 · 已过自动测试）

**现状（问题）**
- `VoicePipeline._slicePreRoll()` 在 `onSpeechStart`（判定**完成**时刻，第 6 帧）从环形缓存尾部往前切 `PRE_ROLL_MS=256ms`。
- 判定完成时刻比 VAD 判定**窗口起点**（第一帧 ≥0.4）晚 6 帧，实际覆盖的是"开口后 ~320~576ms"段，**摸不到开口最开头**；代码注释的"开口前 256ms"语义与数值（256 < 576）不自洽。

**目标方案**
- 锚点：**判定窗口起点**（第一帧被判为人声的帧），而非判定完成时刻。
- 回退量：爬坡期 + 余量（建议 2~4 帧 ≈ 192~384ms，❓ 需按开口弱音段实测标定）。
- 取值位置：环形缓存需**记录每帧时间戳**；稳闸触发时定位"窗口起点帧"，从起点帧往前取预卷段。
- 备选实现：启用库的 `preSpeechPadFrames=N`（触发时从窗口起点往前补 N 帧，业务侧取库产出的 preRoll 数据）。
- 影响：preRoll 真正覆盖"开口开头"；与后端复核窗口（最近 512ms）的拼接对齐更好。

**待办**：实测开口弱音段的概率爬坡帧数 → 定回退量；实现后对比新旧 preRoll 覆盖区间。

## 2. 后端物理复核：能量基线改"头部取" + preRoll 退出物理判据（✅ 已实施 · 已过自动测试）

**现状（问题）**
- 物理复核素材 = `confirm_audio = preRoll + speaking_audio_cache`。
- 能量基线 = `audio_cache[-1024ms:-512ms]`（尾部往前），球球短播时**混入 preRoll 与人声开头**，基线非纯回声；
- preRoll 同时参与能量与占比判据——职责错位（preRoll 是"开口前补字素材"，不该用于能量判断）。

**目标方案**
- 物理判据素材：`session.speaking_audio_cache`（**不含 preRoll**）；preRoll 职责缩为"打断后喂 ASR 补首字 + 闸①长度"，退出能量与占比。
- 能量基线窗口：`cache[0:512ms]`（球球开播段 = **保证纯回声**）。
- 近窗口：`cache[-512ms:]`（用户插话段）。
- 能量闸启用门槛：`len(cache) ≥ ~1200ms`（❓ 实际下限 1088ms，做成可配置）。
  - _隐含假设_：用户插话发生在球球开播 ≥(门槛−576ms)≈624ms 之后，即头部 512ms 全在开口前。
- 短缓存（`len(cache) < 门槛`）：**跳过能量闸 → Silero 占比核验（0.3 严）**（延续现逻辑）。
- 占比分档同步：`len(cache) ≥ 门槛 → 0.05`；否则 `0.3`。
- 占比观察窗口：`cache[-512ms:]`（preRoll 彻底退出物理判据，两处一起改，防留后门）。
- 保留：闸①材料长度 = `len(confirm_audio) ≥ 200ms`（仍用含 preRoll 的总长口径）；`prev_rms > 30` 才对比；`jump < 3.0` 拒绝。

**两套长度判据（实现时务必分清，防混用）**
| 判据 | 长度口径 | 用途 |
|---|---|---|
| 闸① | `len(confirm_audio) ≥ 200ms`（含 preRoll） | 材料充分性 |
| 能量/占比分档 | `len(cache) ≥ 门槛(1200ms)`（不含 preRoll） | 能量闸启用 + 占比松/严 |

**待办**：实测短播（<1200ms）场景漏打断率与 0.3 的适配；实测两档确认率/误报率后定门槛终值。

## 3. barge_latency 前端上报死代码修复（✅ 已实施 · 已过自动测试）

**现状（问题）**
- 前端 `barge_confirm` case：`this.speechStartTime = null` 在 `if (this.speechStartTime !== null)` **之前**执行 → `barge_latency` 消息**永不发出**；
- 后端 `main.py:1454` 已实现接收并统计 `barge_avg`，此链路空转。

**目标方案**

**待办**：修复后验证 `barge_avg` 链路有数据；确认指标口径写入参数清单。

## 4. 打断后保留资源，等语义裁决后才真正丢弃（✅ 已实施 · 已过自动测试）

**现状（问题）**
- `barge_confirm`（后端确认打断）那一刻即执行：`tts.cancel()` + 取消 `tts_task` / `user_speech_task` + `abort_speaking=True`；
- 前端收到 `barge_confirm` 即 `stopStreamPlayback()` 销毁播放器、丢弃已缓冲 TTS 音频；
- 随后 ASR 语义裁决即使判"无效打断（语气词/噪声）"，`resume_playback` 也只是清音量状态——**旧内容已销毁，无法真正恢复**（当前为"名义恢复"）。

**目标方案（把"打断=丢弃旧内容"改为"打断=挂起，语义裁决后再决定丢弃或恢复"）**
- **前端**：
  - `barge_confirm` 改为**挂起播放器**（暂停播放但保留 AudioContext / 已合成未播 PCM / 断点位置 / 时间线），不再销毁；
  - `resume_playback`（语义判"无效"）= 恢复音量 + **从断点续播（或整句重播）**；
  - 新一轮 `reply`/`tts_start`（语义判"有效"）= 才真正释放保留素材、销毁播放器、开始新内容。
- **后端**：
  - 打断确认后**不再无条件** `cancel user_speech_task / tts_task`，改为建立"挂起上下文"（已合成 PCM / 播放断点 / 未消费完的 LLM 流 / 情感参数）；
  - `finish_user_speech` 语义分支：
    - 无效 → `resume_playback` + 附带恢复指令（续播或重播）；
    - 有效 → 清理挂起上下文，走正常新回复流水线；
  - 新增**语义裁决等待超时兜底**（用户一直不说话 / ASR 挂 / 超时 → 强制释放挂起资源，防状态卡死，复用/扩展现有超时体系）。
- **取舍与标定**（❓）：
  - 内存：保留当前句 TTS PCM（KB ~ 百 KB 级，可控）；
  - 恢复粒度：断点续播（体验最优，需保存断点+剩余音频） vs 整句重播（实现简单）；
  - 等待上限时长、与"半完整轮不计入 avg"统计口径的关系。

**涉及位置**：`frontend/renderer/app/voice/VoicePipeline.ts`（`barge_confirm` / `resume_playback` / `reply` case）、`backend/main.py`（`handle_speech_start` 打断分支 / `finish_user_speech` / `handle_user_speech` 取消逻辑）、可能新增挂起上下文数据结构与超时。

**待办**：定恢复粒度（续播/重播）与挂起超时上限；改造后回归"无效打断恢复播报"用例。

## 5. 语义判定流式化：partial 提前判定 + 取消极短文本过滤（✅ 已实施 · 已过自动测试）

**目标**：语义判定不等 `speech_end` / finalize 全文，由流式 ASR partial 驱动尽早出结论。

**方案（backend/main.py）**
- 打断后 ASR 会话的每次 `partial`（stash 全量修订）都经 `_on_semantic_partial` 判定：**出现非语气词内容 → 立即判"有效指令"**（`session.is_effective_interrupt=True`）→ 同步丢弃挂起（`suspended_reply=None`）——旧播报确定不恢复，**不等 speech_end**；
- `finish_user_speech` 决策升级：`effective(流式提前) 或 finalize 文本有效 → 新回复`；否则（空/纯语气词）→ 恢复重播（有挂起）或 `resume_playback`；
- **取消极短文本过滤**：不以文本长度作为恢复/无效判据（原设计中的 `RESUME_MAX_SHORT_CHARS` 不采用）；
- 会话新增 `is_effective_interrupt`（init/断开清理）；5 处打断 ASR partial 回调统一接入语义判定。

**测试（追加到 test_full_link_rework.py）**
- t7：partial 出现"帮我查一下上海天气" → 流式提前判有效、挂起立即丢弃；finalize 返回"嗯"（语气词）仍走新回复（不回恢复重播）；
- t8：partial 全程"嗯/嗯嗯" → 不提前判有效、挂起保留 → finalize 语气词 → 恢复重播；
- t9：静态契约——源码无 `RESUME_MAX_SHORT_CHARS` 长度判据。

**说明**：纯语气词/空的"无效"确认仍需等说完（只有结束才能判定是否为纯语气词）；流式只做**正向提前**，不做负向断言。

## 6. 补充说明窗口（原型：打断后）——已被 #7 泛化为"全体链路端点判定"（✅ 已实施）

> 更正说明：本条目最初把窗口挂在"打断确认后"；经架构澄清，窗口定时器属于**端点检测**而非 barge-in，
> 已由 #7（SmartTurn 端点判定）统一到所有链路（正常收话 + 打断后收话）。本条目保留为原型记录。

**目标**：打断确认后不让用户轮立即"定死提交"，开一个可配置窗口接收可能的补充说明。

**机制（backend/main.py）**
- 打断确认（speaking/pending_play/listening-isPlaying/client_barge_in，4 处）→ `supplement_state="pending"` + `turn_generation+=1`（旧 generation 作废，防泄漏）；
- `speech_end`（pending 态）→ **不再立即 finalize**，转 `SOFT_ENDED` 并 arm `SUPPLEMENT_WINDOW_MS=1200` 定时器；
- 窗口内收到新 `speech_start`（soft_ended 态）→ 回 pending：`turn_revision+=1`、取消窗口定时器、ASR 不 finalize（自然合并前后音频）、旧 LLM/TTS 结果已作废；
- 窗口结束无新语音 → 提交：finalize → 语义判定（有效→新回复；无效→恢复重播，挂起保留）；
- 流式 partial 语义判定（_on_semantic_partial）保持即时，**不受补充窗口阻塞**；
- 会话字段：`supplement_state`/`turn_revision`/`turn_generation`/`_supplement_task`；提交与断开统一清理。
- 阈值口径：首次打断确认与续说确认统一为前端 192ms 档（已按用户确认，不再引入 576ms 后端判据）。

**测试（test_full_link_rework.py 追加，共 12/12）**
- t10：暂断后窗口内不提前提交（无 reply/timing）→ 窗口结束才提交→新回复；
- t11：窗口内续说 → 同一 turn 合并（revision 0→1、窗口重置）→ 最终只提交一次；
- t12：窗口结束语义无效（语气词）→ 恢复重播；
- 既有 t2/t3/t7/t8 适配"等待补充窗口提交"后回归通过。

**预留（Smart Turn）**：`decide_turn_policy(pending/soft_ended, partial, elapsed) → commit/extend` 接口未实现，`SUPPLEMENT_WINDOW_MS` 与提交时点已集中为可注入决策点，后续可在此挂接动态策略。

**待实测**：`SUPPLEMENT_WINDOW_MS=1200` 为上线默认；建议实测"补充说明概率 vs 响应延迟"后微调（窗口越大合并越全、响应越慢）。

## 7. SmartTurn 端点检测（话轮完结判定）（✅ 已实施 · 已过自动测试）

**架构澄清**：窗口定时器与 SmartTurn 属于【端点检测】（用户"是否说完话"→ 何时提交给 STT/LLM），**不是 barge-in**；barge-in 仍是前端 VAD + 后端物理复核（#4）负责。端点判定统一作用于**所有链路**（正常收话 / 打断后收话），不再有"打断专有窗口"。

**方案（backend/smart_turn.py + main.py + 前端）**
- 新增 `SmartTurnJudge`（可插拔 ONNX）：`backend/models/smart_turn_v3.onnx` 放入即启用；缺失 → `available=False` → `judge()` 返回 None → 按 `SMART_TURN_FALLBACK`（默认 direct=直接提交，等价旧行为）；
- **模型已放入**：v3.2-cpu ONNX（8.7MB int8 量化，pipecat-ai/smart-turn-v3 官方仓库）+ `backend/whisper_mel.py`（上游 log-mel 特征复刻，纯 numpy，运行时不依赖 transformers）；推理流程与上游一致：16k PCM → 截/补 8s（保尾）→ Whisper log-mel(80×800) → 模型输出已 sigmoid 概率；
- 前端 `onSpeechEnd`：携带**整段话**（`onSpeechStart` 起累计，含预卷与尾静音，超 `SMART_TURN_MAX_MS=8000` 保尾截断；改造前为"最近 1600ms"切片）→ 后端 `handle_speech_end(ws, session, audio_b64)` 统一端点判定：
  - `p > SMART_TURN_THRESHOLD(0.5)` → 已说完 → **直接提交**（finalize→语义→LLM），不开窗口；
  - `p ≤ 0.5`（或 fallback=window）→ 可能未完 → **开补充窗口** `SUPPLEMENT_WINDOW_MS=1200`：窗口内再说话（`speech_start`，pending/soft_ended 分支）→ 同一 turn 合并（`turn_revision+1`、ASR 不 finalize、旧结果失效）；窗口结束无续说 → 提交；
  - 流式 partial 语义判定（`_on_semantic_partial`）保持即时，**不受端点窗口阻塞**；
- 移除"打断专有 supplement_state=pending"挂点（barge-in 只保留 turn_generation 防泄漏与挂起快照）。

**已验证（真实模型 + 标注数据 + 自动测试）**
- 真实数据探针（`backend/scripts/smart_turn_probe.py`，官方 smart-turn-v3.1-test 20 条带标签语音）：
  - 整段话口径（≤8s 保尾，上游一致）：**18/20 = 90%** 与标签一致；
  - 旧"尾部 1.6s"口径：16/20 = 80%，且把未完样本误判为已说完（#11/#16，p≈0.98）→ 据此把前端切片改为整段话（`SMART_TURN_MAX_MS=8000`）；
  - 已观察的模型边界：超长句（>12s）会被判"未完"（截断信息损失），属已知折衷；
- **阈值标定（31 样本 → θ=0.5）+ 尾静音重判**（`backend/scripts/smart_turn_calib.py`）：
  - 样本构成：**说完 15**（官方标注 10 + edge-tts 中文完句 s1~s4 + 完整犹豫句「嗯 如果 如果说 我想要换一种呢」）；**未完 16**（官方标注 10 + 截断式未完 3 + 犹豫式未完 3（「嗯」/「嗯…如果」/「嗯…如果…如果说」））；
  - 阈值扫描（首判口径）：θ=0.5 → **81%** 一致（未完误判完说 5/16、完说误判未完 1/15）；θ=0.3 → 74%（未完误判 7/16，更差）→ **`SMART_TURN_THRESHOLD=0.5`**（修正初版 0.3——初版只用官方长句集，样本一换结论反转）；
  - **已知边界（记录备查）**：犹豫片段（「嗯」1.10s p=0.981 /「如果」1.42s p=0.901 /「如果说」1.58s p=0.923；截断句 1.5~2.8s p=0.95~0.98）在任何阈值下都判为"完整"——"未完但停顿"在声学上不可分；
  - **职责边界（用户确认）**：SmartTurn 只判"话是否完整"，**不判"是否说完话"**——说完由前端 VAD 静音时长判定（`VoicePipeline.ts` `redemptionFrames`）。据此**移除短片段时长闸**（`SMART_TURN_MIN_COMMIT_MS`/`SMART_TURN_GATED_WINDOW_MS` 方案作废，代码与参数已删除）：p>阈值即提交，短片段「如果」会按独立 turn 提交，是否等待续说完全由静音时长与补充窗口决定；

**修复：占比闸系统性误拒"轻声插话"（基线静音分支）**
- 症状：基线 RMS≤30（mic 几乎听不到球球）时，真插话近窗有明显能量（实测 RMS=137/峰值=1891）仍被判"噪声"（Silero 人声占比 0.00 → barge_reject）——Silero 对低音量语音不敏感。

- 回归：t6b。

**修复：窗口/重判任务"自我取消"导致提交静默死亡**
- 症状：重判 p 高提前提交（或窗口超时提交）时，日志停在 `[ASR调试] finalize 前`，之后无任何输出、无回复。
- 根因：窗口 `_fire` / 重判 `_fire` 都在自身内 `await finish_user_speech`，而 `finish_user_speech` 开头调用 `_cancel_supplement_window` / `_cancel_endpoint_rejudge` → **取消的正是当前任务自己**；生产 AliyunASR `finalize` 内有真实 await（`to_thread`），CancelledError 在那里抛出 → 提交链路整个死亡。
- 修复：两个 cancel 助手跳过 `asyncio.current_task()`（外部取消——合并/断开/新一轮——不受影响）。
- 回归保障：MockASR.finalize 增加 `await asyncio.sleep(0)` 模拟真实 await 点（此前 mock 无 await，自取消测不出来）。

**修复：窗口期 vad_cancel 误杀 ASR 会话（增量 ASR 链路缺口）**
- 症状：未说完开窗（p≤0.5）后，若前端 VAD 对噪声/软语音误报发 `vad_cancel`，旧代码无条件 `asr.reset()` + `is_user_speaking=False` → 窗口结束 `finalize` 拿到已销毁会话 → 返回空 → 走"语气词"分支不进 LLM（用户实测：p=0.145 开窗后无回复）。
- 修复（main.py `handle_control_message` vad_cancel 分支）：`soft_ended` → 忽略（窗口照常提交）；`pending`（续说中）→ 回退 `soft_ended` + 重挂窗口（保留会话与音频、保证提交）。正常场景（无窗口）行为不变。
- 增量 ASR 语义确认（providers/asr.py）：`feed` = 入队非阻塞、同一 WS 会话 FIFO 累积；窗口期不 finalize/不重启，续说音频直接追加同会话；超时 `finalize`（commit）返回整句文本 → 进 LLM。

**待实测标定**：说完的判定在**前端 VAD 静音时长**（`VoicePipeline.ts` `redemptionFrames=20` → 640ms，与 F6 口径统一；可调 `frontend` `frameSamples`）；端点侧 `SUPPLEMENT_WINDOW_MS` 与 `SMART_TURN_REJUDGE_MS` 按真实用户语流微调；`SMART_TURN_LOG_AUDIO=1` 收集真实语音后可再做一轮更准的标定。

## 9. 管理网关/控制面板联调修复 + 构建环境修复（✅ 已实施 · 已过验证）

> **背景**：用户反馈"控制面板看不到对应文档及内容、历史记录也看不了"。排查后确认**前后端协议与数据关联本身正确**（真实后端 `/ws/mgmt` 全链路实测 9/9），问题出在"运行环境 + 网关回退目标"两层叠加。本节记录根因、三项代码修复与使用注意。

### 9.1 根因（两层叠加）

1. **真实后端（8001）未运行** → 网关（`frontend/main/services/gateway.ts`）按设计连续 2 次失败后自动回退到备用 Mock；

- 根因：Starlette `build_middleware_stack` 用**关键字** `cls(app=app, ...)` 构造中间件，而 `__init__` 首参名为 `inner`。

- 回归防护（新增两层）：

**② Mock 端口 9000 → 9100（backend/mock_server.py + 前端网关/探测脚本/契约文档）**
