## 一、对话能力层

### M2.1 · 拟人度主观评分（MOS，1–5 分）

**测什么**：宠物说话"像不像人"。

**怎么测**：
1. 准备 20–40 组**对话样本**（覆盖：日常闲聊 / 情绪回应 / 被打断 / 主动开口）
2. **LLM 评测**（轨道 A）：强模型按 rubric 打分，每个样本评 2 次取中位
3. **人工校准**（轨道 B）：3–5 人抽样 20% 复核

**rubric 锚点**：
- 5: 无法分辨是否 AI
- 4: 高度拟人，偶有机械感
- 3: 像 AI 但有"人味"
- 2: 明显是 AI 但能对话
- 1: 完全机械

**数据从哪来**：会话 JSONL（`backend/session_store.py` 全量持久化，README 已承诺）

**当前值**：待测（Demo 阶段缺样本集）
**目标值**：≥ 4.0（面试讲"向 4 分迈进"即可，不用数字过硬）

---

### M4.1 · 工具调用成功率

**测什么**：单次工具调用是否能成功返回。

**怎么测**：
1. 跑 50–100 次固定任务（"查天气" "计算" "搜索"）
2. 定义成功 = 返回结果 **非错误** 且被 LLM **正确消费**（在回复中引用）
3. 从 agent 日志解析 `tool_call_id` + 结果状态

**数据从哪来**：`backend/agent_runtime.py` 原生 function calling 日志（天然有 `tool_call_id`）

**当前值**：可测（代码已就绪，缺一次批量跑）
**目标值**：≥ 95%

---

### M4.2 · 多步任务完成率

**测什么**：需要 ≥2 次工具调用的链路任务完整跑通的比例。

**怎么测**：
1. 设计 15–20 个多步任务（如 "查天气 → 根据天气提醒带伞"）
2. 完整链 = 所有步骤工具都成功 + 最终回答与中间结果一致
3. 全程从日志判定

**数据从哪来**：同上（`agent_runtime.py`）

**当前值**：可测（任务集要新写）
**目标值**：≥ 80%

---

### M5.1 · 人设一致性

**测什么**：回答是否符合"年年"人设（撒娇/傲娇/委屈/犯困），有没有出戏。

**怎么测**：
1. 取对话样本（同一批 20–40 组）
2. **LLM 评测**：prompt 中给出人设定义（来自 `backend/voice_style.py`），请模型对每一轮回答判"出戏/不出戏"
3. **人工校准**：出戏判定的分歧点人工看

**注意**：人设一致性 ≠ 拟人度——**机器人设稳定但机械** vs **人设一致且拟人**是两个概念。面试这里可展开。

**数据从哪来**：会话 JSONL + `voice_style.py` 人设定义

**当前值**：待测
**目标值**：出戏率 < 10%（即一致性 ≥ 90%）

## 二、系统能力层

### M6.1 · E2E 延迟（p50 / p95）

**测什么**：用户说完 → 宠物开始发声的耗时。

**两级定义（注意区分，这是面试时会被追问的点）**：
- **服务端 E2E（`run_metrics.py` 自动测）**：ASR(mock 0.5s) + LLM 首句 + TTS 首包，不含前端播放延迟——用于迭代定位是"谁慢了"
- **真实 E2E（手动测）**：前端 `VAD speech_end` → 第一帧音频出声，含 ASR 真实耗时 + 网络 + 播放器——这才是用户感知的数字

**怎么测（服务端，脚本自动）**：
1. `python tests/run_metrics.py` —— 跑 11 条文本用例（跳过 ASR 直接喂文本）
2. 从 `timing` 消息取 `e2e`，重复统计 p50 / p95
3. 目的：定位瓶颈（LLM 首句 vs TTS 首包）

**怎么测（真实，手动）**：
1. testboard 打开，自己说话
2. 看前端 `client_real_e2e` 上报（`last_real_e2e_ms`）或 DevTools 时间线
3. 重复 30 次取 p50 / p95

**数据从哪来**：服务端 = `run_metrics.py` timing 消息（`main.py` `_build_timing_stats`）；真实 = 前端 `last_real_e2e_ms`

**当前值**：服务端脚本待跑；真实 E2E 实测待补
**目标值**：p50 < 2s / p95 < 3s（这是"能聊"和"卡"的分界）

---

### M6.2 · barge-in 响应延迟（p50 / p95）

**测什么**：宠物正在说话，用户插话 → 宠物停声的耗时。

**怎么测**：
1. 播放一段 TTS 音频，中途注入"人声"
2. 记录 `t1` = 前端 VAD 触发 `speech_start`；`t2` = 播放器收到 `barge_confirm` 停止播放
3. 重复 30 次取 p50 / p95

**数据从哪来**：前端 `speech_start` + `stopStreamPlayback` 时间戳（`frontend/index.html` 已有事件流）

**当前值**：待测（双层打断已实现，理论极快）
**目标值**：p50 < 200ms / p95 < 400ms（"不粘"的体验）

---

### M6.3 · 误停率（反向指标）

**测什么**：用户没插话（或只是环境音），但 TTS 被停了。

**怎么测**：
1. 播放 TTS 音频，注入**非人声噪声**（咳嗽/关门声/音乐）各 10 次
2. 数"被停了"的次数
3. 误停率 = 停止次数 / 注入次数

**数据从哪来**：同 M6.2 的插话测试台

**当前值**：待测
**目标值**：≤ 10%（极严格，说明体感层 + 业务层双层都稳）

---

### M7.1 · 误打断率

**测什么**：后端确认了打断，但用户其实没说话。

**怎么测**：
1. 播放 TTS 音频，注入噪声（音乐/咳嗽/关门）
2. 数后端发出 `barge_confirm` 的次数
3. 误打断率 = `barge_confirm` 数 / 注入数

**数据从哪来**：后端状态机日志（`barge_confirm` / `barge_reject` 事件）

**当前值**：待测
**目标值**：≤ 5%（后端二次确认应显著低于前端误报率）

---

### M7.2 · 端到端成功率

**测什么**：一轮完整对话（说→听→想→答→播）成功的比例。

**怎么测**：
1. 跑 50 轮完整对话（混合正常 / 打断 / 长句）
2. 定义成功 = 进入到 `speaking` 且正常播完，无超时 / 无错误分支
3. 失败按原因归类（ASR 失败 / LLM 失败 / TTS 失败 / 超时）

**数据从哪来**：状态机日志（`idle/listening/thinking/speaking/error` 状态转移）

**当前值**：待测
**目标值**：≥ 90%

---

### M7.3 · 长会话稳定性

**测什么**：30+ 轮长会话是否能稳定跑完。

**怎么测**：
1. 自动化脚本连续跑 30–50 轮（含打断）
2. 判定项：不崩溃 / 不卡死（无超时悬挂）/ 状态机能回到 `listening` / 上下文压缩正常触发
3. 跑 3 次取平均

**数据从哪来**：状态机日志 + 上下文压缩日志（`backend/compaction.py` 有触发点）

**当前值**：可测（压缩逻辑已实现）
**目标值**：3 次全成功（100%）

---

### M7.4 · 漏打断率（反向指标）

**测什么**：用户真在插话，系统却没识别、继续播放。

**怎么测**：
1. 播放 TTS，注入**真实人声**（提前录好的人说话）
2. 数"没被打断"的次数
3. 漏打断率 = 未停次数 / 注入次数

**注意**：漏打断率与误停率是**对偶**——误停率低可能因"几乎不打断"，漏打断率高；反之亦然。**两者必须同时看**，面试讲这一层是加分的。

**数据从哪来**：同 M6.2 插话测试台

**当前值**：待测
**目标值**：≤ 5%（该停必停）
